# Chapter 7

# useEffect — Synchronizing with the Outside World

> "The biggest misunderstanding about `useEffect` is thinking that it exists to run code after rendering.
>
> That's only a side effect of what it really does.
>
> **Its real purpose is to synchronize your component with something outside of React.**"

This chapter will completely change the way you think about `useEffect`.

Most React developers memorize things like:

- "Runs after render."
- "Dependency array controls execution."
- "Cleanup prevents memory leaks."

Those are all true.

But they don't explain **why** `useEffect` exists.

Let's build it from first principles.

---

# Before React

Imagine plain JavaScript.

```js
const input = document.querySelector("input");

input.focus();
```

Question.

Why are we calling

```js
focus()
```

Because we want to change

something outside

our JavaScript variables.

The browser has a DOM.

Our code wants to synchronize

with that DOM.

---

Another example.

```js
window.addEventListener("resize", handler);
```

Question.

Where is

that event listener stored?

Not inside your variables.

It lives

inside the browser.

Again

our code

is synchronizing

with something outside itself.

---

Another example.

```js
fetch("/users");
```

The network

is outside React.

The server

is outside React.

The browser timer

is outside React.

Everything here

is external.

---

# React's Philosophy

React likes one simple idea.

```
State

↓

UI
```

Nothing more.

React wants rendering

to be

a pure calculation.

```
Given

State + Props

↓

Return JSX
```

Notice something.

No

```
fetch()

setInterval()

focus()

localStorage()

WebSocket()

document.title
```

These are not calculations.

These are

side effects.

---

# What Is A Side Effect?

A side effect is

**anything that affects something outside the current render.**

Examples

✅ Network requests

✅ Timers

✅ DOM manipulation

✅ Event listeners

✅ localStorage

✅ WebSockets

✅ Analytics

❌ Calculating

```jsx
count * 2
```

Not a side effect.

That's just computation.

---

# Why Can't We Put Side Effects Inside Render?

Suppose

```jsx
function App(){

    fetch("/users");

    return <div>Hello</div>;

}
```

Question.

What happens

every render?

React calls

```jsx
App()
```

again.

Therefore

```
fetch()

↓

fetch()

↓

fetch()

↓

fetch()
```

One network request

per render.

Not what we wanted.

---

Another example.

```jsx
function App(){

    setInterval(()=>{

        console.log("Hello");

    },1000);

}
```

Question.

What happens

after five renders?

```
Interval A

Interval B

Interval C

Interval D

Interval E
```

Five intervals.

All running.

Disaster.

---

# React Separates Rendering From Effects

Think of React

as having two phases.

```
Phase 1

↓

Render

↓

Calculate JSX
```

Nothing else.

Then

```
Phase 2

↓

Commit UI

↓

Run Effects
```

This separation

is one of React's biggest design decisions.

---

# The Render Phase

During rendering

React asks

one question.

```
What should the UI look like?
```

Not

```
What network request should I make?
```

Not

```
Should I open a WebSocket?
```

Only

```
What should the screen look like?
```

---

# The Commit Phase

After React

updates the DOM

it finally says

Now

it's safe

to perform

side effects.

That's when

```
useEffect()
```

runs.

---

# Mental Timeline

```
State Changes

↓

React Renders

↓

Creates New Closures

↓

Calculates JSX

↓

Updates DOM

↓

Runs Effects
```

Notice

Effects happen

after rendering.

Not during rendering.

# The First Effect

```jsx
useEffect(()=>{

    console.log("Hello");

});
```

Question.

When does this run?

After

every render.

Because

no dependency array

was provided.

# Why Is The Callback A Closure?

Let's inspect.

```jsx
useEffect(()=>{

    console.log(count);

});
```

Question.

What is this?

```jsx
()=>{

    console.log(count);

}
```

It's a function.

Every function

is a closure.

Question.

Which render

does it belong to?

The render

that created it.

Exactly like

`useCallback`

Exactly like

`useMemo`

Exactly like

event handlers.

---

# React Doesn't Execute It Immediately

During render

React receives

this closure.

```
Closure

↓

Store It
```

Render finishes.

DOM updates.

Then

React executes

that stored closure.

---

# Dependency Arrays Revisited

Consider

```jsx
useEffect(()=>{

    console.log(count);

},[]);
```

Question.

How many closures

does React create?

Every render

creates

a brand new closure.

Wait...

Didn't we say

the effect only runs once?

Yes.

This is subtle.

---

# Render 1

Creates

```
Closure A
```

Dependencies

```
[]
```

React stores it.

Runs it.

---

# Render 2

Creates

```
Closure B
```

JavaScript always does.

Question.

Does React use it?

No.

React compares

dependencies.

Nothing changed.

So React ignores

Closure B.

Closure A

remains

the active effect.

This explains

stale closures.

---

# The Dependency Array Is Not About JavaScript

JavaScript

always creates

new closures.

The dependency array

only tells React

whether

to replace

the previously active effect.

---

# Visual Timeline

```
Closure A

↓

Effect Runs
```

---

Render 2

```
Closure B

↓

Ignored
```

---

Render 3

```
Closure C

↓

Ignored
```

Closure A

remains active.

# Now Change A Dependency

```jsx
useEffect(()=>{

    console.log(count);

},[count]);
```

Render 1

```
Closure A
```

Runs.

---

Render 2

```
count

changed
```

React says

Old closure

is no longer valid.

Destroy it.

Replace it

with

```
Closure B
```

Run

Closure B.

---

# This Is Synchronization

Imagine

```jsx
useEffect(()=>{

    document.title = count;

},[count]);
```

Question.

What is React synchronizing?

The component state

with

the browser tab title.

Whenever

```
count
```

changes

the browser title

must also change.

This is synchronization.

# The Cleanup Function

Suppose

```jsx
useEffect(()=>{

    const id=setInterval(...);

},[]);
```

Question.

Who stops

the interval?

Nobody.

It keeps running.

React gives us

cleanup.

---

```jsx
useEffect(()=>{

    const id=setInterval(...);

    return ()=>{

        clearInterval(id);

    };

},[]);
```

Question.

When does cleanup run?

Two situations.

---

# Situation 1

Component unmounts.

```
Component

↓

Removed

↓

Cleanup Runs
```

---

# Situation 2

Dependencies change.

Render 1

```
Closure A

↓

Interval A
```

Render 2

Dependency changes.

Question.

Should

Interval A

continue?

No.

React first executes

Cleanup A.

Then

creates

Interval B.

---

# Order Of Events

When dependencies change

React does

```
Old Cleanup

↓

New Effect
```

Not

the other way around.

This prevents

duplicate subscriptions.

---

# Memory Diagram

Render 1

```
Effect A

↓

WebSocket A
```

---

Render 2

Dependency changes.

React performs

```
Disconnect WebSocket A

↓

Create WebSocket B
```

Perfect synchronization.

---

# Why ESLint Is So Strict

Consider

```jsx
useEffect(()=>{

    socket.send(message);

},[]);
```

Question.

Can

```
message
```

change?

Yes.

Question.

Will React

replace

the effect?

No.

Dependency array

is empty.

Now

the socket

keeps sending

the first message forever.

ESLint warns you

because

the synchronization

is broken.

# useEffect Is Not A Lifecycle Method

Many developers think

```
componentDidMount

↓

useEffect([])
```

This comparison

helps beginners.

But it hides

the real idea.

A better mental model is

> "Keep this external system synchronized with these dependencies."

That sentence

works

for every effect.

---

# One Powerful Rule

Whenever you write

```jsx
useEffect(...)
```

Ask yourself

> **What external system am I synchronizing with?**

If you can't answer

that question,

you probably

don't need

an effect.

---

# Interview Questions

## Why does useEffect run after rendering?

Because rendering should remain a pure calculation.

Effects synchronize with external systems after React commits the UI.

---

## What does the dependency array actually mean?

It tells React

when the currently active effect closure has become invalid

and should be replaced by a new one.

---

## Why do stale closures happen inside useEffect?

Because every render creates a new closure,

but React may continue using an older one until dependencies change.

---

## When does the cleanup function execute?

1. Before a new effect replaces the old one.
2. When the component unmounts.

---

## Should every piece of logic go inside useEffect?

No.

Only logic that synchronizes with something outside React.

Pure calculations belong inside rendering.
