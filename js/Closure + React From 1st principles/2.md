# Chapter 2

# React's Render Cycle, State Snapshots, and Why Every Render Creates a New Closure

> "The biggest mistake React developers make is assuming a component is an object that keeps changing.
>
> It isn't.
>
> A React component is a function that is executed again and again."

---

# Before We Begin

Everything we learned in Chapter 1 was pure JavaScript.

We now know:

- Functions create Execution Contexts.
- Execution Contexts own Lexical Environments.
- Closures remember Lexical Environments.
- Every function invocation creates a brand new Lexical Environment.

Now we're going to answer one question.

---

# The Question

Consider this component.

```jsx
function Counter() {

    const [count, setCount] = useState(0);

    function handleClick() {
        console.log(count);
    }

    return (
        <button onClick={handleClick}>
            {count}
        </button>
    );
}
```

Question.

How many

```
handleClick
```

functions exist?

One?

Or many?

Most React developers answer

```
One
```

That answer is completely wrong.

---

# React Components Are Not Objects

Suppose someone tells you

> "The component updates."

That sentence is technically incorrect.

React does **not** update your component.

React simply calls your function again.

Think about normal JavaScript.

```js
function add(a, b) {
    return a + b;
}

add(2, 3);
add(5, 7);
add(10, 20);
```

Question.

Did JavaScript update the previous function call?

No.

It executed the function again.

React components work exactly the same way.

---

React calls

```jsx
Counter();
```

Execution Context

```
Counter()

↓

Execution Context

↓

count = 0

↓

handleClick()

↓

Closure
```

The JSX is produced.

React renders it.

Done.

# User Clicks Button

```jsx
setCount(1);
```

Question.

Does React modify

```
count = 0
```

No.

This is one of the biggest misconceptions in React.

---

# What React Actually Does

Instead of changing the old execution context,

React schedules another render.

Conceptually

```
Render 1

↓

Execution Context A

↓

count = 0
```

Later

```
Render 2

↓

Execution Context B

↓

count = 1
```

Notice something.

Execution Context A

still exists

until nothing references it.

React did not update it.

It created another one.

---

# This Is Extremely Important

React State

is **not**

a mutable variable.

Instead

every render receives

its own snapshot.

Think of it like taking photographs.

---

# Snapshot Analogy

Render 1

📷

```
count = 0
```

---

Render 2

📷

```
count = 1
```

---

Render 3

📷

```
count = 2
```

Every render is a new photograph.

You never edit an old photograph.

You simply take another one.


The render where it was created.

# Wait...

If Every Render Creates New Functions...

Why Doesn't Everything Break?

Excellent question.

Imagine this.

```
Render 1

↓

Button

↓

handleClick A
```

User hasn't clicked yet.

React re-renders.

```
Render 2

↓

Button

↓

handleClick B
```

React updates the DOM.

The button now points to

```
handleClick B
```

The old handler is disconnected.

This is why clicking later prints

the newest state.

# State Doesn't Live Inside Your Component

This surprises almost everyone.

Question.

Where is

```
count
```

actually stored?

Inside

```jsx
Counter()
```

?

No.

If it were,

React would lose it every render.

Instead

React stores state internally.

Conceptually

```
React

↓

State Storage

↓

count = 2
```

When React renders

```jsx
Counter()
```

it injects

the latest snapshot.

---


imagine

React doing something like

```js

    state: 0

});
```

Later

```js

    state: 1

});
```

Later

```js

    state: 2

});
```

Each function call

receives

a different snapshot.

# Why setState Doesn't Immediately Change count

Consider

```jsx
function Counter() {

    const [count, setCount] = useState(0);

    function click() {

        setCount(1);

        console.log(count);

    }

}
```

Prediction.

What gets printed?

Many beginners answer

```
1
```

Wrong.

Output

```
0
```

Why?

Because

```
count
```

belongs to

the current render.

Calling

```
setCount()
```

does **not**

modify

the current snapshot.

It schedules

another render.

Current render

```
count = 0
```

Future render

```
count = 1
```

---

# The Rule

Every closure

belongs

Never multiple renders.

Question.

Which

```

```

Answer

The one from

# Interview Question

Does React update variables?

Answer

No.

React calls the component again,

creating a new execution context with a new state snapshot.

---

# Interview Question

Does setState modify the current closure?

Answer

No.

It schedules another render.

The current closure continues to see the values from the render in which it was created.

---

# Interview Question

Why does every render create a new handleClick?

Answer

Because the component function executes again.

Every function execution creates new variables and new closures.

# Chapter Summary

You now understand:

- Components are functions.
- React never updates a component instance.
- React calls the component again.
- Every render creates a new Execution Context.
- Every render creates a new Lexical Environment.
- Every render creates new closures.
- State behaves like immutable snapshots.
- Closures belong to one render forever.
- setState schedules another render instead of mutating the current closure.

You now know enough to understand one of the most misunderstood concepts in React:

> **Stale Closures**

And once stale closures make sense,

`useRef`, `useCallback`, `useMemo`, and `useEffect` become almost inevitable.
