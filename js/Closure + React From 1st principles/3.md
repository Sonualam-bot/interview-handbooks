# Stale Closures — The Biggest React Bug You'll Ever Debug

> "React is not remembering old state.
>
> Your function is."

---

# Introduction

By now we know three important facts.

### Fact 1

Every render creates a brand new Execution Context.

---

### Fact 2

Every render creates brand new variables.

---

### Fact 3

Every function created during that render becomes a closure over **that render's variables.**

That means

Every render owns

its own closures.

Keep that sentence in your head.

Everything in this chapter depends on it.

---

# The Most Important Mental Shift

Many React developers imagine this.

```
Component

↓

count

↓

Updated
```

This picture is wrong.

React does **not**

update variables.

Instead

React creates

new variables.

```
Render 1

↓

count = 0



Render 2

↓

count = 1



Render 3

↓

count = 2
```

Three renders.

Three completely different variables.

---

# What Is A Stale Closure?

Let's define it first.

> A stale closure is a closure that still references variables from an older render after newer renders have already happened.

Notice something.

The closure isn't broken.

React isn't broken.

JavaScript isn't broken.

The closure is behaving **exactly** as JavaScript promised.

It is remembering

the environment

where it was created.

The bug comes from

our expectation.

---

# The First Example

```jsx

    const [count, setCount] = useState(0);

        setTimeout(() => {

        },3000);

    return (
        <button onClick={handleClick}>
            Click
        </button>
    );

}
```

Question.

Suppose

```
count = 0
```

User clicks.

Immediately afterwards

User increments

```
count
```

to

```
5
```

Three seconds later

What gets printed?

Most beginners answer

```
5
```

Wrong.

Output

```
0
```

Output

It simply remembered

where it was born.

# The Important Realization

The bug

is not

that the closure became stale.

The bug

is

that we expected

a closure

to update itself.

Closures

never

update themselves.

# Why Dependency Arrays Exist

Many developers think

dependency arrays

are

"when to rerun an effect."

That's true.

But it's incomplete.

A better definition

is

> Dependency arrays tell React when the current closure has become invalid and a new closure should be created.

Read that again.

That sentence explains

the entire dependency array.

# Why ESLint Complains

Consider

```jsx
useEffect(()=>{

    console.log(user.name);

},[]);
```

Question.

Can

```
user
```

change?

Yes.

Question.

Will React create

a new closure?

No.

Dependency array

is empty.

Therefore

the closure always remembers

the first

```
user
```

ESLint warns you

because it can detect

that you're creating

a stale closure.

# Interview Question

Why does this print

```
0
```

forever?

```jsx
useEffect(()=>{

    setInterval(()=>{

        console.log(count);

    },1000);

},[]);
```

Correct answer

The interval callback is a closure created during the first render.

The empty dependency array prevents React from creating a new closure.

Therefore

the callback forever references

the first render's

```
count.
```
