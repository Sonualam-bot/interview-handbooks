# Chapter 1C

# Closures, Memory, Multiple Instances, and Why React Depends on Them

> "A closure is not a feature added to JavaScript.
> It is the inevitable consequence of lexical scoping and garbage collection."

---

# Before We Continue

At this point we know:

- Every function execution creates an Execution Context.
- Every Execution Context owns a Lexical Environment.
- Functions remember the Lexical Environment where they were created.
- Returning a function keeps that Lexical Environment alive.

Now we're going to answer some questions that every experienced JavaScript developer eventually asks.

- Can two closures have different memories?
- Can multiple closures share one memory?
- When does JavaScript finally free that memory?
- Why doesn't memory leak forever?
- Why does React rely so heavily on closures?

# Chapter 1.7

# Every Function Call Creates a New Lexical Environment

Consider this.

```js
function createCounter() {

    let count = 0;

    return function () {

        count++;

        console.log(count);

    };

}
```

Now execute

```js
const counter1 = createCounter();

const counter2 = createCounter();
```

Question.

Do they share the same

```
count
```

variable?

Most beginners answer

```
Yes
```

because the code is identical.

That answer is wrong.

---

# Why?

Remember

Every function call creates

a brand new Execution Context.

Therefore

```
createCounter()

↓

Execution Context A

↓

Lexical Environment A

↓

count = 0
```

Second call

```
createCounter()

↓

Execution Context B

↓

Lexical Environment B

↓

count = 0
```

Those environments never meet.

---

# Memory Picture

```
counter1

↓

Lexical Environment A

count

↓

0
```

Completely separate from

```
counter2

↓

Lexical Environment B

count

↓

0
```

Same code.

Different memory.

---

# Execution

```js
counter1();
```

Output

```
1
```

Memory

```
counter1

↓

count = 1
```

---

Now

```js
counter1();
```

Output

```
2
```

Memory

```
counter1

↓

count = 2
```

---

Now

```js
counter2();
```

Output

```
1
```

Not

```
3
```

Why?

Because

```
counter2
```

owns

its own lexical environment.

---

# This Is One Of The Most Important Closure Concepts

Every invocation creates

an entirely new universe.

Even if the code is identical.

The code is shared.

The memory is not.

---

# Visual Representation

Always.

# Chapter 1.8

# Multiple Closures Sharing One Environment

Now let's reverse the situation.

```js
function createCounter() {

    let count = 0;

    function increment() {

        count++;

    }

    function decrement() {

        count--;

    }

    function value() {

        console.log(count);

    }

    return {

        increment,

        decrement,

        value

    };

}
```

Question.

How many

```
count
```

variables exist?

One.

Not three.

---

# Memory

```
Lexical Environment

count

↓

0

↑

↑

↑

increment

decrement

value
```

Three closures.

One variable.

---

# Execution

```js
const counter = createCounter();
```

Memory

```
count = 0
```

---

```js
counter.increment();
```

Memory

```
count = 1
```

---

```js
counter.increment();
```

Memory

```
count = 2
```

---

```js
counter.decrement();
```

Memory

```
count = 1
```

---

```js
counter.value();
```

Output

```
1
```

Notice

Every closure sees

the latest value.

Because

they all reference

the same variable.

---

# Variables

Not Snapshots

Suppose closures copied values.

Memory would look like

```

↓

count = 0

decrement

↓

count = 0

↓

```

That would be useless.

Instead

JavaScript stores

Everyone references it.

# Chapter 1.9

# When Does JavaScript Finally Destroy A Closure?

Question.

If closures keep environments alive,

won't JavaScript eventually run out of memory?

Excellent question.

The answer is

No.

Because of

Garbage Collection.

---

# Reachability

JavaScript follows one simple rule.

Memory is kept

only while

something can still reach it.

Suppose

```
counter

↓

Closure

↓

Lexical Environment

↓

count
```

Everything is reachable.

Memory stays alive.

---

Now

```js
counter = null;
```

Memory becomes

```
null



Closure

↓

Lexical Environment

↓

count
```

Can anything reach

the closure anymore?

No.

Can anything reach

the lexical environment?

No.

Eventually

Garbage Collector removes everything.

---

# Very Important

JavaScript does NOT destroy memory immediately.

Garbage Collection happens

later.

The exact timing

depends on the JavaScript engine.

You should never rely on

when

Garbage Collection happens.

Only that

it eventually will.

# Common Misconceptions

### ❌ "Closures copy variables."

False.

They reference variables.

---

### ❌ "Closures only happen when returning a function."

False.

Callbacks create closures.

Event listeners create closures.

Timers create closures.

Promise callbacks create closures.

React components create closures.

Hooks rely on closures.

---

### ❌ "Closures leak memory."

False.

Unreachable closures are garbage collected.

Poor code can create memory leaks.

Closures themselves are not leaks.

---

### ❌ "Each closure has its own copy of variables."

Sometimes.

Different function invocations create different lexical environments.

Multiple closures from the same invocation share one environment.

These are two completely different situations.

---

# Interview Questions

### Question 1

Why doesn't JavaScript destroy the lexical environment immediately after a function returns?

Answer:

Because a returned function may still reference it. As long as the lexical environment is reachable through a closure, the garbage collector cannot reclaim it.

---

### Question 2

Do closures copy variables?

Answer:

No.

Closures remember references to variables inside their lexical environment.

---

### Question 3

Do two calls to the same function share one lexical environment?

```js
const a = createCounter();

const b = createCounter();
```

Answer:

No.

Every invocation creates a completely new lexical environment.

---

### Question 4

Can multiple closures share one lexical environment?

Answer:

Yes.

If they were created during the same function execution, they all reference the same lexical environment.
