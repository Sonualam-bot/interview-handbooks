# Chapter 1.1

# A Very Simple Question

Consider this code.

```js
function greet() {
    let name = "Sonu";

    console.log(name);
}

greet();
```

Most developers look at this code and think:

> "The function prints Sonu."

That answer is correct.

But it ignores everything that actually happened.

The JavaScript engine performed dozens of operations before printing anything.

As engineers, we care about those operations.

Because every advanced JavaScript concept eventually depends on them.

---

# What Actually Happens?

When JavaScript reaches

```js
greet();
```

it **does not immediately execute the function body.**

Instead, the engine prepares an environment where that function can safely run.

Think about it.

The function needs somewhere to store

- variables
- parameters
- function declarations
- the value of `this`
- references to outer variables

Where should JavaScript keep all of that?

The answer is

> An Execution Context.

---

# Definition

An Execution Context is the environment JavaScript creates whenever code begins executing.

Every function call creates a brand new Execution Context.

Every.

Single.

Time.

---

# Visualizing It

Imagine JavaScript is running this.

```js
greet();
```

Before the first line executes, JavaScript silently creates something like this.

```
Execution Context

-----------------------

Variables

Functions

this

Lexical Environment

-----------------------
```

Nothing has executed yet.

The engine is preparing the workspace.

---

# Think Like an Operating System

Imagine you open Microsoft Word.

Before you type even one character,

Windows allocates

- memory
- CPU resources
- a process
- handles
- buffers

Only then can Word begin working.

JavaScript does something similar.

Before your function executes,

it prepares everything that function needs.

That preparation is called

```
Execution Context
```

# Chapter 1.2

# Every Function Gets Its Own World

Consider

```js
function first() {
    let x = 10;
}

function second() {
    let x = 20;
}

first();
second();
```

Question.

How can both functions have a variable named

```js
x
```

without conflicting?

Because they never share memory.

Each function gets its own Execution Context.

```
first()

↓

Execution Context

x = 10
```

Completely separate from

```
second()

↓

Execution Context

x = 20
```

Those are different environments.

Different memory.

Different variables.

---

# A Common Misconception

Many beginners believe

```
Variable names must be unique.
```

They don't.

Variables are only unique **inside their own Execution Context.**

That is why this works perfectly.

# Chapter 1.3

# What Lives Inside an Execution Context?

An Execution Context is not one giant object.

Conceptually, it contains several important pieces.

```
Execution Context

│

├── Variable Environment

├── Lexical Environment

├── this

└── Function Metadata
```

Today we care about one thing more than everything else.

The

```
Lexical Environment
```

Because closures are built on top of it.

---

# Chapter 1.4

# Lexical Means "Written"

This word scares many developers.

It shouldn't.

The word

```
Lexical
```

simply means

> Based on where something is written in the source code.

Not where it executes.

Where it is **written.**

---

Example

```js
function outer() {

    function inner() {

    }

}
```

Where is

```
inner
```

written?

Inside

```
outer
```

That relationship is called

```
Lexical
```

It is determined by the source code itself.

Not by runtime.

---

# Another Example

```js
function A() {

    function B() {

        function C() {

        }

    }

}
```

The lexical relationship is

```
A

↓

B

↓

C
```

This relationship never changes.

No matter how many times you execute the program.

# Chapter 1.5

# What Is a Lexical Environment?

Imagine JavaScript enters

```js
function greet() {

    let name = "Sonu";

    let age = 26;

}
```

JavaScript creates something conceptually similar to

```
Lexical Environment

name

↓

"Sonu"

age

↓

26
```

Think of it as

> A table that maps identifiers to values.

Whenever JavaScript needs a variable,

it first looks inside this table.

---

# Variable Lookup

Consider

```js
let name = "Sonu";

console.log(name);
```

How does JavaScript know what

```
name
```

means?

It searches the Lexical Environment.

```
Lexical Environment

name

↓

"Sonu"
```

Found.

Return the value.

Done.

Simple.

# Chapter 1.6

# Nested Functions

Now let's make things interesting.

```js
function outer() {

    let name = "Sonu";

    function inner() {

        console.log(name);

    }

}
```

Question.

Where is

```
name
```

stored?

Inside

```
outer
```

Question.

Does

```
inner
```

have a variable named

```
name
```

No.

Then why does this work?

That question is the beginning of closures.

---

# JavaScript Doesn't Stop Searching

When JavaScript evaluates

```js
console.log(name);
```

it performs a lookup.

Step 1

Search inside

```
inner
```

```
Inner Environment

name

❌ Not Found
```

Then what?

Does JavaScript throw an error immediately?

No.

Instead,

it asks

```
Who is my lexical parent?
```

Answer

```
outer
```

Search there.

```
Outer Environment

name

↓

"Sonu"
```

Found.

Return it.

---

# The Search Algorithm

JavaScript follows this process.

```
Current Environment

↓

Found?

↓

Yes

↓

Return value

↓

No

↓

Move to Parent Lexical Environment

↓

Repeat

↓

Eventually reach Global Environment

↓

Still not found?

↓

ReferenceError
```

This algorithm is called

```
Lexical Scope Resolution.
```

Everything about closures depends on this single algorithm.

---

# Chapter Summary

In this chapter we learned:

- Every function call creates a new Execution Context.
- Every Execution Context has its own variables.
- Variable names do not conflict across different Execution Contexts.
- A Lexical Environment is a mapping between identifiers and values.
- "Lexical" means "determined by where the code is written."
- JavaScript searches the current Lexical Environment first, then walks outward through parent lexical environments until it finds the identifier or reaches the global scope.

We have not created a closure yet.

But we have built every concept required to understand **why closures are even possible**.
