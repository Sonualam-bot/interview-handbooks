# Chapter 1B

# The Birth of Closures

> "Closures were not invented so JavaScript developers could write clever code.
> They are a natural consequence of how lexical environments work."

---

# The Question We Left Unanswered

Consider this code.

```js
function outer() {

    let count = 0;

    function inner() {
        console.log(count);
    }

    return inner;
}

const fn = outer();

fn();
```

Output

```text
0
```

This program appears simple.

But it forces JavaScript to answer a very difficult question.

After this line executes

```js
const fn = outer();
```

the function

```
outer()
```

has already finished.

Normally when a function finishes,

its Execution Context should disappear.

Right?

Then where is

```
count
```

coming from?

That single question is the reason closures exist.

---

# What Most Developers Imagine

Many beginners imagine JavaScript executes like this.

```
outer()

↓

Create Execution Context

↓

count = 0

↓

Return inner

↓

Destroy everything
```

If this were true,

what would happen here?

```js
fn();
```

JavaScript would try

```js
console.log(count);
```

But

```
count
```

would no longer exist.

This program should crash.

Yet it doesn't.

Therefore,

our mental model is wrong.

---

# What Actually Happens

Let's execute the program step by step.

---

## Step 1

JavaScript reaches

```js
outer();
```

Execution Context is created.

```
Execution Context

count = 0

inner -> function
```

Nothing surprising.

---

## Step 2

JavaScript creates

```js
function inner() {

    console.log(count);

}
```

Question.

Does JavaScript copy

```
count
```

inside

```
inner
```

No.

This is the first huge misconception.

Nothing gets copied.

Instead,

JavaScript records

> "This function was created inside this lexical environment."

Conceptually

```
inner

↓

Lexical Environment

↓

outer Environment
```

It remembers **where it was born.**

Not what values existed.

---

# Think Like a Child

Imagine a child is born in a house.

Years later,

the child moves away.

The child doesn't take the house.

The child simply remembers

where home is.

A closure works similarly.

The function remembers

its home environment.

It does **not** carry copies of variables.

---

# Step 3

Now JavaScript reaches

```js
return inner;
```

Question.

What is being returned?

Not

```js
inner()
```

We're not executing it.

We're returning

the function object itself.

Conceptually

```
Function Object

Code

+

Pointer to Lexical Environment
```

That second line is the important one.

---

# Memory Picture

After

```js
return inner;
```

Imagine memory looks like this.

```
Heap

-------------------

Function Object

↓

Code

↓

Pointer

↓

Lexical Environment
```

Notice something.

The Lexical Environment is still reachable.

Therefore,

Garbage Collector cannot remove it.

---

# Garbage Collection Rule

JavaScript does **not** free memory just because a function returns.

Memory is freed only when

nothing references it anymore.

This is one of the most important rules in JavaScript.

Think about this statement carefully.

A function ending

≠

Memory disappearing.

Those are completely different events.

---

# Why Doesn't JavaScript Delete It?

Imagine JavaScript immediately deleted

```
count
```

after

```
outer()
```

returned.

Then this

```js
fn();
```

would fail.

JavaScript would have broken its own language.

Instead,

the engine notices

```
Someone still needs this environment.
```

Therefore,

it keeps it alive.

---

# The Real Definition of a Closure

Most books say

> A closure is a function bundled together with its lexical environment.

That definition is correct.

But incomplete.

A better definition is

> A closure is created when a function survives beyond the lifetime of the execution context in which it was created.

Read that sentence again.

That is the entire magic.

The function survives.

Therefore,

its lexical environment must survive too.

---

# Closures Remember Variables

Not Values

This distinction is incredibly important.

Consider

```js
function outer() {

    let count = 0;

    function increment() {
        count++;
    }

    function print() {
        console.log(count);
    }

    return {
        increment,
        print
    };
}
```

Question.

Are there two copies of

```
count
```

No.

There is only one.

Both functions reference

the same variable.

---

# Visual Memory Diagram

```
Lexical Environment

count

↓

0

↑          ↑

increment  print
```

Two functions.

One variable.

# Execution

Notice

`print`

It simply looked at

# Another Huge Misconception

Many developers think

```
Closure

↓

Stores values
```

Wrong.

Closures store

references

to variables.

That is why changes become visible.

Imagine if JavaScript copied values.

```
increment

↓

count = 0

print

↓

count = 0
```

Each function would have its own copy.

The output would never become

```
2
```

Since JavaScript prints

```
2
```

we know

there must be one shared variable.

# Closures Can Share State

This property makes closures extremely powerful.

Without classes.

Without objects.

Without private fields.

We already have

private state.

Example

```js
function createCounter() {

    let count = 0;

    return {

        increment() {

            count++;

        },

        decrement() {

            count--;

        },

        value() {

            return count;

        }

    };
}
```

Question.

Can anyone access

```
count
```

directly?

No.

```
count
```

only exists inside the lexical environment.

The outside world cannot reach it.

Only the closures can.

---

# This Is Data Encapsulation

Notice something interesting.

JavaScript gave us

private state

long before

private class fields existed.

Closures were the original way to create private variables.

Many JavaScript libraries written before ES6 rely heavily on this technique.

---

# Interview Question

What does a closure capture?

Correct answer:

> It captures references to variables in its lexical environment.

Incorrect answers:

- It copies variables.
- It stores values.
- It duplicates memory.

None of those are true.

# Chapter Summary

In this chapter we learned

- Returning a function does not destroy its lexical environment.
- Garbage Collection removes unreachable memory, not finished functions.
- A closure remembers its lexical environment.
- Closures store references to variables, not copies of values.
- Multiple closures can share the same lexical environment.
- Closures naturally provide private state.

We have now built the foundation.
